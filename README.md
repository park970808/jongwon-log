# 종원 공동 활동일지 — Firestore 시험판

알한글/rhwp의 실제 웹 편집기에 Yjs와 Firestore 전송 계층을 연결했습니다. 칸별 잠금 없이 같은 셀의 글을 함께 입력하며, 본문·표·서식을 포함한 HWPX 문서 전체를 다룹니다. 3팀의 실제 Firebase에 연결하며, 초대 링크를 통해 팀원이 가입합니다. 기존 일지는 `/legacy/index.html`에서 계속 사용할 수 있습니다. 복잡한 한글 문서의 모든 편집 충돌을 검증한 것은 아니므로 시험판으로 제공합니다.

## 실행

Node.js 22.12 이상 권장. 저장소 루트에서:

```sh
npm ci
npm run dev
```

표시된 로컬 주소를 열고 **기기 내 체험**을 누릅니다. 링크를 같은 브라우저의 다른 탭에 붙여 넣으면 동시 편집을 확인할 수 있습니다. 이 체험은 로컬 브라우저끼리만 연결되며 Firestore에 저장하지 않습니다.

팀원들과 다른 컴퓨터에서 사용하려면 관리자가 전달한 초대 링크로 접속해 **Firestore 문서 열기**를 사용합니다. 3팀 운영 규칙과 초대가 적용되어 있습니다. 2팀·장원급제는 별도 Firebase 관리자 연결이 필요합니다. [배포 안내](DEPLOYMENT.md).

```sh
npm run build
npm run preview
```

배포 대상은 생성된 **dist 폴더 전체**입니다. `index.html`은 진입점이지만 JavaScript, WASM, 폰트가 필요하므로 HTML 한 파일만 업로드하거나 더블클릭해서 실행할 수 없습니다. GitHub Pages의 프로젝트 하위 경로를 지원하도록 상대 경로로 빌드합니다.

## 사용 흐름

1. 팀·이름·주차·문서 ID를 입력하고 Firestore 문서를 엽니다.
2. 처음 만드는 문서는 기본 활동일지 양식을 사용하거나 HWPX를 가져옵니다.
3. **링크 복사**로 동일한 문서 주소를 공유합니다. 팀 편집 권한을 받은 사용자가 같은 문서를 엽니다.
4. 같은 셀을 여러 사람이 입력할 수 있습니다. 글자 서식과 표 행 추가도 변경 기록으로 공유됩니다.
5. **Firestore에 저장됨**을 확인하거나 **HWPX 내려받기**로 파일을 받습니다.

기존 화면과 양식은 `legacy/`에 보존했습니다. 기존 화면에서 **한글 파일 내보내기** → 새 공동 문서에서 HWPX 가져오기로 이전합니다. 기존 Firestore 문서를 자동 변경하거나 삭제하지 않습니다. 옛 화면과 새 문서는 이전 후 서로 다른 문서이므로 양쪽 수정이 자동 교환되지는 않습니다.

## 구조

```text
알한글 웹 편집기 (studio.html / WASM)
          ↕ 로컬 변경 분석 · 원격 변경 반영
HWPX 문서 구조 ↔ Yjs 문서 (텍스트·서식·표·첨부 개체)
          ↕ 변경 묶음 / IndexedDB 복구본
Firestore 업데이트 로그 ↔ 다른 팀원의 브라우저
          ↓ 선택 배포
일일 체크포인트 함수 (원본 로그는 유지)
```

- `src/document-model.js`: HWPX XML ↔ 공유 문서, 텍스트 병합, 스타일/이미지 참조 정규화.
- `src/editor-binding.js`: 실제 편집기와 공유 문서 연결, 조합 입력 대기, 개인 실행 취소.
- `src/sync-provider.js`: 업데이트 압축·해시 검증·영속 outbox·재시도, 입력 멈춤 기준 묶음 전송, 증분 재열기, 손상 기록 격리, 리스너 자동 재연결, 클라이언트 체크포인트.
- `src/firestore-backend.js`: 추가 전용 로그. 작은 변경은 기록 1장(인라인), 256 KiB 초과만 128 KiB 청크. 접속자 커서.
- `src/presence-policy.js`, `src/checkpoint-policy.js`: Spark 무료 한도에 맞춘 커서·압축 정책.
- `functions/`: 선택적 서버 체크포인트(Blaze 요금제). Spark에서는 브라우저가 체크포인트를 만들며, 두 방식 모두 같은 검증(`coveredUntil` = 포인터)을 거칩니다.
- `vendor/rhwp/`: MIT 라이선스 rhwp v0.8.6 편집기와 제공된 알한글 DMG의 호환 WASM.

HTML 전체를 Firestore의 한 필드에 덮어쓰지 않습니다. Yjs 변경은 중복·역순 수신에도 병합되며, HWPX 구조로 다시 내보내 편집기에 반영합니다. 전송은 Firestore만 사용하며 별도의 협업 WebSocket 서버는 없습니다.

## 검증

```sh
npm test
```

실제 Chrome 편집기 검사와 Firebase 에뮬레이터 검사는 [TESTING.md](TESTING.md)를 참고하세요. 같은 셀의 동시 한글 입력, 상대방 글을 보존하는 실행 취소, 오프라인 재접속, 새로고침 복원, 글자 굵게, 한글 조합 이벤트, 표 행 추가, 권한 규칙, 체크포인트 경계를 검증했습니다.

## 현재 범위와 제한

- 기본 활동일지 양식의 Chrome 데스크톱 동시 편집을 검증했습니다. 임의의 모든 한글 문서·기능·브라우저에 대한 호환성을 보장하는 버전은 아닙니다.
- 행 추가/삭제·가로 셀 병합과 다른 사용자의 입력, 같은 위치의 동시 행 추가, 사진 두 장 동시 삽입을 검증했습니다. 서로 겹치는 병합/분할·이동, 머리말/각주 커서, 선택 영역 보존과 새 글꼴 동시 추가는 추가 검증이 필요합니다.
- 네이티브 내보내기의 문단 ID가 재생성되므로 내용 기반으로 문서 노드를 대응합니다. 문단 이동/삭제와 동시 입력처럼 모호한 경우는 안정 ID를 직접 제공하는 엔진 통합이 후속 과제입니다.
- 원격 반영은 문서 재렌더링 방식입니다. 반영 중 발생한 일반 텍스트·한글 조합·키 이벤트는 보관 후 재생합니다. 큰 문서의 지연, 복합 붙여넣기와 선택 영역 안정성은 추가 검증이 필요합니다. 반영 중 붙여넣기는 일반 텍스트로 보관합니다.
- 한 번의 압축 변경 묶음/체크포인트는 최대 4 MiB, 해제 후 최대 96 MiB입니다. 큰 사진 문서는 제한될 수 있습니다. Firebase Storage를 통한 별도 이미지 저장은 아직 구현하지 않았습니다.
- 체크포인트가 있어도 원본 로그를 삭제하지 않습니다. Spark(무료) 한도에 맞춘 사용량은 아래 "Firestore 무료 한도"를 참고하세요.
- 인증은 익명 Firebase UID + 초대 링크 가입 방식입니다. 브라우저 데이터 삭제/기기 변경 시 원래 초대 링크를 다시 열어 가입합니다. 영구 계정 로그인과 초대 관리 화면은 후속 작업입니다.
- 오류 발생 시 편집을 멈추고 **복구 데이터 받기**로 Yjs 원본과 화면의 HWPX를 보존합니다. Yjs 복구본 자동 업로드 UI는 아직 없습니다.

## Firestore 무료(Spark) 한도

하루 쓰기 20,000 · 읽기 50,000이며 미국 태평양 자정(한국 오후 4~5시)에 초기화됩니다. 변경 기록 하나는 쓰기 1회와 열려 있는 창 수만큼의 읽기이므로, 기록 수 × 창 수를 줄이는 것이 핵심입니다.

- **묶음 전송**: 입력이 멈추면 보내고, 계속 입력해도 최대 간격을 넘기지 않습니다. 함께 연 사람이 1명 이하면 1.2초 멈춤/최대 4초, 많을수록 2초 멈춤/최대 9초(6명)로 늘립니다(`batchForPeers`). 보내기 전의 입력도 이 기기에 저장되어 있어 잃지 않습니다.
- **인라인 기록**: 256 KiB 이하 변경은 문서 1장에 담습니다(이전: 기록+조각 2장, 보내기 전 확인 읽기 1회). 이전 버전 탭이 열려 있는 동안은 자동으로 예전 형식을 씁니다.
- **증분 재열기**: 다시 열 때는 이 기기에 있는 내용 이후의 기록만 읽습니다. 새 기기는 체크포인트(압축본)와 그 이후 기록만 읽습니다. 체크포인트가 없거나 손상되면 전체 기록을 읽습니다.
- **커서**: 다른 문단으로 옮길 때 3초 안에, 같은 문단 안 이동과 대기 중 신호는 60초마다, 5분 넘게 아무것도 안 하면 10분마다 보냅니다. 숨긴 탭은 "자리 비움"만 한 번 보냅니다.
- **오프라인 캐시**: 잠깐의 재연결이 전체 재조회로 과금되지 않습니다.

`node scripts/firestore-usage-model.mjs`는 실제 묶음·커서 코드를 시나리오에 적용합니다. 6명이 1시간 동안 같은 문서를 열고 각자 20분 입력, 이번 주 기존 기록 2회분, 1인 1회 새로고침:

| 시나리오 | 쓰기 (하루 한도 대비) | 읽기 · 최악 기준 | 읽기 · 규칙 과금 없을 때 |
| --- | --- | --- | --- |
| 이전 방식 | 37,693 (188%) | 1,231,213 (2,462%) | 2,186% |
| 현재 · 각자 쓰던 기기 | 1,553 (8%) | 23,696 (47%) | 29% |
| 현재 · 매번 새 기기 | 1,777 (9%) | 27,620 (55%) | 37% |
| 하루 전체 · 각자 기기 (위 1시간 + 7시간 화면만 켜 둠) | 1,835 (9%) | 28,646 (57%) | 35% |
| 하루 전체 · 새 기기 | 2,059 (10%) | 32,570 (65%) | 43% |

"최악 기준"은 실시간으로 받는 문서마다 보안 규칙의 `exists()`가 읽기 1회로 다시 과금된다고 가정한 값입니다(공식 문서로 확인되지 않아 보수적으로 잡음). 모델 가정과 1건당 비용은 스크립트 상단에 있고, `tests/usage-model.test.js`가 최악 기준으로도 이 범위를 벗어나는 변경을 막습니다. 이 수준의 집중 작성을 하루에 두 번 이상 하면 최악 기준으로 한도에 가까워질 수 있으니 Firebase Console → Firestore → 사용량을 확인하세요. 한도를 넘어도 입력은 이 기기 outbox에 보관되고 초기화 후 자동 저장됩니다.
